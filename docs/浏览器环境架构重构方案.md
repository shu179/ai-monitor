浏览器环境管理架构重构方案

## 当前问题

1. **目录混用**：`user_data/` 同时存储应用配置和浏览器数据
2. **路径混乱**：三种路径并存（legacy auth/、fresh browser_auth_profiles/、shared user_data/）
3. **隐式依赖**：豆包等平台隐式使用 user_data/ 作为浏览器上下文
4. **清理困难**：重置浏览器环境时可能误删应用配置

## 新架构设计

### 目录结构

```
~/Library/Application Support/AIBrandMonitor/
├── config.yaml                          # 应用配置
├── app_data/                            # 应用数据（新）
│   ├── daily_task_status.json
│   ├── scheduler_state.json

│   └── ...
├── browser_profiles/                    # 浏览器环境（新，统一）
│   ├── doubao/
│   │   └── default/                     # 默认环境
│   │       ├── Default/

└── exports/                             # 导出
```

### 核心原则

1. **职责分离**：应用数据和浏览器数据完全分离
2. **路径统一**：所有平台使用统一的 browser_profiles/ 结构
3. **显式管理**：每个平台都有明确的目录，不再隐式共享
4. **易于清理**：重置浏览器环境不会影响应用配置

### 迁移策略

#### 阶段一：兼容旧数据（当前实现）
- 保留 `auth/` 和 `user_data/` 的读取逻辑
- 新环境使用 `user_data/browser_auth_profiles/`
- 通过 metadata 管理多个 profile

#### 阶段二：统一路径（推荐实现）
- 将所有浏览器数据迁移到 `browser_profiles/`
- 将应用配置迁移到 `app_data/`
- 废弃 `auth/` 和 `user_data/` 的浏览器用途

#### 阶段三：清理遗留（未来）
- 删除旧的 `auth/` 目录
- `user_data/` 只保留向后兼容的符号链接

## 实现方案

### 方案 A：渐进式迁移（推荐）

**优点**：
- 不破坏现有环境
- 用户可以选择迁移时机
- 兼容性好

**缺点**：
- 代码复杂度高
- 需要维护多套逻辑

**实现**：
1. 添加新的 `browser_profiles/` 路径
2. 首次启动时提示用户迁移
3. 提供一键迁移工具
4. 保留旧路径的读取逻辑（只读）

### 方案 B：强制迁移（激进）

**优点**：
- 代码简洁
- 架构清晰
- 易于维护

**缺点**：
- 破坏现有环境
- 需要重新登录所有平台

**实现**：
1. 启动时检测旧目录
2. 自动备份并迁移
3. 删除旧目录
4. 只支持新路径

### 方案 C：混合方案（当前采用）

**优点**：
- 快速解决当前问题
- 不影响其他平台

**缺点**：
- 架构仍然混乱
- 未来需要再次重构

**实现**：
1. 保持现有逻辑
2. 只修复豆包的路径问题
3. 通过 reset 工具清理
